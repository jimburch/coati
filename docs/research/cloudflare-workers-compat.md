# What breaks on Cloudflare Workers (SvelteKit + `adapter-cloudflare`)

Research for jimburch/coati#371. No migration is planned; this is a compatibility survey to keep current auth/architecture decisions from foreclosing a future Workers move. Sources are Cloudflare, SvelteKit, Lucia/Arctic/Oslo, Drizzle, Shiki, Sentry, and Better Auth primary docs/repos, plus repo facts cited as `file:line`. Research date: 2026-09-24; several of the cited upstream statuses (Lucia, Arctic) changed within 2025–2026, so re-check dates before acting.

## 1. Postgres access on Workers

Cloudflare's Hyperdrive documentation states that **node-postgres (`pg`) is the recommended driver** and **Postgres.js is also supported**, with minimum versions `pg@8.13.0` / `postgres@3.4.4`, and that Drizzle and Kysely are supported ORMs (min. `drizzle-orm@0.26.2`) — the repo's `postgres@^3.4.8` and `drizzle-orm@^0.45.1` (`package.json`) both clear these bars. Hyperdrive requires `nodejs_compat` to be enabled for the driver to run ([Hyperdrive: Connect to PostgreSQL](https://developers.cloudflare.com/hyperdrive/configuration/connect-to-postgres/)).

Critically, Hyperdrive's docs say to **create a new client per request** rather than hold a pool in the Worker: "Hyperdrive maintains the underlying database connection pool, so creating a new client is fast" (node-postgres) and "creating a new client on each request is fast and recommended" (postgres.js); their own postgres.js example caps `max: 5` "due to Workers' limits on concurrent external connections" (same page). The current code creates one module-level `postgres()` client with `{ max: 20, idle_timeout: 30, connect_timeout: 10 }` at `src/lib/server/db/index.ts:6` — this pattern (module-scoped long-lived pool, `max: 20`) is exactly what Hyperdrive's docs say not to do on Workers, and would need to become a per-request client construction, plus the pool size dropped well under 5.

Drizzle's query builder usage itself (`drizzle-orm/postgres-js`, schema in `src/lib/server/db/schema.ts`) needs no rewrite if you stay on Postgres via Hyperdrive — same dialect, same schema, same `drizzle-kit` migrations.

**D1 (SQLite) alternative**: Cloudflare's D1 limits page ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)) lists a 10 GB max database size (paid), 30-second max query duration, a 2 MB max row/BLOB size, and "up to six connections... for each invocation" — but does not list FTS5 or any SQLite extension support anywhere on that page. This means the `tsvector` generated column and GIN index at `src/lib/server/db/schema.ts:173-181` (used for setup search) has no direct D1 equivalent; a move to D1 would require rebuilding full-text search from scratch (SQLite FTS5 isn't available, per the absence of any extension support in Cloudflare's own limits doc — this is an inference from omission, not an explicit "not supported" statement, so treat it as the weaker of the two DB findings). D1 would also require rewriting the entire `dialect: 'postgresql'` Drizzle schema and all `drizzle-kit` migrations to SQLite dialect — a full schema fork, not a config change. **Given the existing `tsvector` search feature, Hyperdrive + Postgres is the path that preserves the current schema; D1 is a bigger rewrite.**

## 2. Lucia v3, Arctic, and auth alternatives

**Lucia is deprecated.** The current lucia-auth.com homepage states: "Lucia was deprecated in March 2025," and points to a single-file replacement (`code/auth_session.ts`) instead of the npm package ([lucia-auth.com](https://lucia-auth.com/)). The original announcement, in [lucia-auth/lucia discussion #1707](https://github.com/lucia-auth/lucia/discussions/1707) (Oct 7, 2024), says: "Lucia will be an open source resource on implementing auth with JavaScript. Instead of installing a package, you'll learn how to implement sessions from scratch," citing database adapters as "a significant complexity tax." That same discussion states the author "will continue to develop all my other libraries, including Arctic and Oslo" — a claim since overtaken by events (see below).

The recommended replacement pattern (Lucia's own "roll your own sessions" guide referenced from lucia-auth.com) is a plain session table + token hashing implementation — structurally identical to what's already in `src/lib/server/auth.ts` (`createSession`/`validateSessionToken`/`invalidateSession` against a `sessions` table, token hashed via `node:crypto`). **Coati's existing auth code already is the "post-Lucia" pattern** — it doesn't import the `lucia` package at all, just `arctic` and `node:crypto`, so Lucia's deprecation has no code impact here; it does mean there is no upstream package to lean on going forward.

**Arctic is also deprecated**, contrary to what the 2024 discussion promised. The current arcticjs.dev homepage states: "Arctic was deprecated in July 2026" and directs users to example replacement code under `/code` in the [pilcrowonpaper/arctic](https://github.com/pilcrowonpaper/arctic) repo. The author's own announcement ([pilcrowonpaper.com/blog/18](https://pilcrowonpaper.com/blog/18)) says he "haven't touched the project in nearly a year," calls it "very bloated with the number of providers," and states Oslo's packages are deprecated too except `@oslojs/encoding` (kept only until `Uint8Array.toBase64()`/`fromBase64()` land natively in Node, "around 2028"). The repo's reference replacement code (e.g. `code/authorization_code_exchange.ts`) is built on `fetch`, `URLSearchParams`, and `Uint8Array.toBase64()` — all Web-standard APIs with no Node-specific imports, so it is Workers-portable, but it is example code to copy, not a maintained dependency.

**Does the current Arctic usage run on Workers today?** Functionally yes — Arctic's OAuth flows are fetch-based, and Coati's usage (`src/lib/server/auth.ts:1,13`, device flow in `src/routes/api/v1/auth/device/+server.ts`) is plain `fetch()` calls to GitHub's REST/OAuth endpoints plus `node:crypto` for token generation, both Workers-supported per Cloudflare's Node compatibility matrix (below). The risk isn't runtime compatibility, it's that Arctic (like Lucia) is now an unmaintained snapshot.

**Alternatives worth naming**: Better Auth has an official Cloudflare Workers/Hono integration doc ([better-auth.com/docs/integrations/hono](https://better-auth.com/docs/integrations/hono)) stating it uses `AsyncLocalStorage` and requires the `nodejs_compat` (or narrower `nodejs_als`) compatibility flag — i.e. it is documented as Workers-runnable, provided that flag is set. There is a community-maintained `better-auth-cloudflare` package layering D1/Hyperdrive/KV/R2 bindings on top ([zpg6/better-auth-cloudflare](https://github.com/zpg6/better-auth-cloudflare)) — this is third-party, not first-party Better Auth, so treat its specific claims (D1/Hyperdrive/R2 wiring) as secondary-sourced. Note also a since-closed GitHub issue ([better-auth/better-auth#1143](https://github.com/better-auth/better-auth/issues/1143), opened Jan 2025) reporting Better Auth "cannot function properly in edge environments like Cloudflare Workers" due to needing dynamic env/binding access at init time — this predates the current official Hono/Workers doc, so it reads as a historical rough edge that's since been addressed, but I could not confirm the exact fix/PR that closed it.

## 3. Node-only APIs actually used in `src/` and `packages/`

Grep results (excluding `.svelte-kit`/`build` output and `node_modules`):

- `node:crypto`: `src/lib/server/auth.ts:2`, `src/lib/server/auth.test.ts:2`, `src/routes/api/v1/auth/device/+server.ts:1`. Bare `crypto` import: `src/lib/server/queries/teams.ts:4` (`randomBytes`). Cloudflare's Node.js compatibility matrix lists Crypto as "🟢 supported" ([developers.cloudflare.com/workers/runtime-apis/nodejs/](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)) — no change needed, works once `nodejs_compat` is on.
- `fs`/`path`: `src/lib/utils/vite-version-plugin.ts:1-2` (a Vite plugin — runs at build time on the machine running `vite build`, never shipped into the Worker bundle) and `src/lib/assets/agents/icons.test.ts:2-3` (Vitest test, not runtime code). Neither is a Workers concern.
- `process.env`: `src/lib/server/rate-limit.ts:39` (`DISABLE_RATE_LIMIT`), `src/lib/server/observability/env.ts:4`, `src/lib/observability/mixpanel-client.ts:8`, plus several `*.integration.test.ts` files. SvelteKit's own env pattern (`$env/dynamic/private` / `$env/static/private`, already used elsewhere, e.g. `src/lib/server/auth.ts:6`) is the portable equivalent; raw `process.env` reads work under `nodejs_compat` but SvelteKit's adapter-cloudflare docs favor `platform.env` / the `$env` modules for bindings-based config ([SvelteKit: Cloudflare](https://svelte.dev/docs/kit/adapter-cloudflare)).
- `Buffer`: no direct usage found in `src`/`packages` (`grep -rn "Buffer\." ` returned nothing outside node_modules).
- `child_process`: none found in `src`/`packages`.
- No other `node:*` imports were found in `packages/agents-registry` or `packages/shared-validation`.

Cloudflare's Node compatibility matrix additionally lists `node:fs` as "🟢 supported," but its own `fs` reference page clarifies this is a **virtual filesystem**: bundled files are read-only under `/bundle`, and `/tmp` is writable but "not persistent and are unique to each request" and count against the Worker's memory limit ([Cloudflare: Node.js fs](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/)). Nothing in the current repo does real fs writes at runtime, so this is informational, not a fix-list item.

## 4. mdsvex/shiki, Sentry, and file storage

**Correction to the issue's framing: mdsvex is not actually a dependency.** `grep -rn "mdsvex"` across the repo (excluding `node_modules`) returns no hits, and it is absent from `package.json`. Markdown is rendered at request time with `marked` + `shiki`, not compiled with `mdsvex`, in `src/lib/server/markdown.ts`.

- **Shiki**: `src/lib/server/markdown.ts:2,9-15` calls `createHighlighter(...)`, Shiki's default configuration, which loads its Oniguruma engine. Shiki's own docs state the JS regex engine's advantage is that "it doesn't require loading a large WebAssembly file for Oniguruma," while the WASM engine is preferred "if you run Shiki on Node.js... and bundle size or WebAssembly support is not a concern" ([shiki.style/guide/regex-engines](https://shiki.style/guide/regex-engines)). Shiki's docs did not, in the fetched excerpt, explicitly name Cloudflare Workers, but the stated trade-off (large WASM binary vs. bundle-size-conscious JS engine) directly maps onto the Workers 64 MiB script-size ceiling ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)); switching to `createJavaScriptRegexEngine()` is the documented way to avoid the WASM load. Treat the "designed for Workers" framing as my inference from Shiki's stated trade-off, not a verbatim Shiki claim about Cloudflare.
- **`isomorphic-dompurify`**: used at `src/lib/server/markdown.ts:3` to sanitize the rendered HTML. Its `package.json` (`node_modules/isomorphic-dompurify/package.json`) declares a hard dependency on `jsdom`. Cloudflare's own architecture (workerd, a V8-isolate sandbox with no native Node bindings) is documented to reject packages needing native/system-level bindings, and community reports (e.g. [cloudflare/workers-sdk#4913](https://github.com/cloudflare/workers-sdk/issues/4913)) describe native-binding packages failing to resolve under Wrangler's bundler — I could not find a Cloudflare-authored statement naming `jsdom` specifically, so this is inference from the general native-bindings constraint plus the dependency graph, not a direct primary-source "jsdon doesn't work" citation. Practically, this is the piece most likely to need replacing (e.g. a Workers-safe sanitizer, or moving sanitization to the client where a real DOM exists).
- **Sentry**: `src/hooks.server.ts:13-17` calls the generic `@sentry/sveltekit` `Sentry.init()`/`Sentry.setContext`/`Sentry.captureException` API. Sentry's own Cloudflare + SvelteKit guide ([docs.sentry.io/.../cloudflare/frameworks/sveltekit/](https://docs.sentry.io/platforms/javascript/guides/cloudflare/frameworks/sveltekit/)) still uses the `@sentry/sveltekit` package, but requires wiring `initCloudflareSentryHandle()` and `sentryHandle()` (composed via `sequence()`) into `hooks.server.ts`'s `handle` export, and `handleErrorWithSentry` into `handleError` — i.e. Sentry has a Cloudflare-specific initialization path that supersedes a bare `Sentry.init()` call. This is a rewire of `src/hooks.server.ts:16-17,132-159`, not a package swap.
- **SetupFile content storage**: `src/lib/server/db/schema.ts:225` stores file `content` as Postgres `text`. Per CLAUDE.md's own documented decision, "File contents stored in PostgreSQL text columns for MVP (config files are tiny, <10KB)." D1's row/BLOB limit is 2 MB per row ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)), comfortably above that. Cloudflare positions R2 for "unstructured data" at larger scale/egress-sensitive workloads ([developers.cloudflare.com/r2/](https://developers.cloudflare.com/r2/)), not as a requirement at current file sizes. **No forced change here** unless the product decision to allow larger/binary setup files changes.

## 5. Other blockers found in the repo

- **In-memory rate limiting** (`src/lib/server/rate-limit.ts:31-32`, `RateLimiterMemory`): the file's own comment block (lines 4-30) already documents that this doesn't survive multi-process deployment and names `RateLimiterPostgres`/`RateLimiterRedis` as drop-in fixes for the current PM2/Node deployment. On Workers the same root problem is more acute — each isolate is short-lived and not guaranteed to persist between requests — so the fix path (shared state in Postgres via Hyperdrive, or a Cloudflare-native primitive like the Workers Rate Limiting API / Durable Objects / KV) is required, not optional, before a Workers move.
- **`setInterval` background scheduler** (`src/lib/server/scheduler.ts:10-16`, started at `src/hooks.server.ts:16` on module load): refreshes a Postgres materialized view every 15 minutes via a long-lived timer. Cloudflare's Workers limits doc describes execution as trigger-based (HTTP request, Cron Trigger, Queue consumer, Durable Object alarm) and does not describe any supported form of persistent background execution between invocations ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)); Cron Triggers are documented as "ideal for running periodic jobs, such as for maintenance" with a minimum granularity of one minute ([Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)). This is a hard blocker as currently written — it needs to become a Cron Trigger (or Durable Object Alarm) invoking the refresh, not a `setInterval` fired at module scope.
- **Worker bundle size**: Cloudflare's limit is 64 MiB uncompressed for both Free and Paid plans ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). No single dependency here looks close to that ceiling on its own, but Shiki's WASM engine, `jsdom`, and Sentry's SDK are exactly the class of dependency Cloudflare and SvelteKit's own docs call out as bundle-size risks ("Wrangler will fail to publish your worker if it exceeds the size limits... unless some large libraries are included," per SvelteKit's adapter-cloudflare docs) — worth a real bundle analysis before migrating, not just a docs check.
- **CPU time**: Free plan is capped at 10ms CPU time per request; Paid defaults to 30s (configurable to 5 min) ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Syntax highlighting a full setup's files with Shiki on first render could be CPU-heavy; not a blocker on a paid plan, but worth keeping in mind for cold-start/highlighting-heavy routes.
- No cron/queue/Durable Object usage exists in the repo today (`grep -rn "cron\|Durable\|scheduled"` returned nothing outside the scheduler discussed above), and there is no `wrangler.toml`/`wrangler.json` in the repo — the app has never been configured for Workers.

## Implications for decisions made before the migration

- **Auth**: The existing hand-rolled session table + `node:crypto` hashing in `src/lib/server/auth.ts` already matches the pattern Lucia's own maintainers now recommend post-deprecation, and depends only on `node:crypto` (Workers-supported) and Drizzle/Postgres (works via Hyperdrive). **This part of the current design survives a Workers move essentially unchanged.** Continuing to build directly on Lucia-as-a-package would not be forward-looking regardless of Workers (it's deprecated everywhere); continuing to build on Arctic is now in the same boat — it still runs, but there's no upstream fixing bugs or adding providers. If a package (rather than hand-rolled code) is wanted going forward, Better Auth is the one with an actual maintained Workers/Hono integration path today; adopting it now rather than later would avoid rewriting the session/OAuth layer twice.
- **Database**: Any decision to lean further into Postgres-only features — the `tsvector`/GIN full-text search column being the clearest example — is safe under a future Hyperdrive-based Workers deployment (Postgres stays Postgres) but would need to be re-architected from scratch under a D1/SQLite migration path. If a Workers move is plausible, avoid adding more Postgres-specific SQL (window functions are fine either way, but generated columns / extensions like `tsvector`, `pg_trgm`, etc. are not portable to D1). The connection-per-request / small-pool pattern Hyperdrive requires is a code change but not a schema or architecture change — safe to defer.
- **Rate limiting and the scheduler**: Both are already flagged in-repo as not surviving horizontal scaling (rate limiter) or, implicitly, a serverless/edge model (interval-based scheduler). Fixing these for "many Node processes" (Postgres/Redis-backed rate limiter, a real job scheduler/cron) happens to be the same fix needed for Workers — doing this work now is not wasted even if Workers doesn't happen.
- **Markdown/Sentry/observability**: These are the most "swap later without regret" items — `renderMarkdown`/`highlightCode` and Sentry initialization are already isolated behind small modules (`src/lib/server/markdown.ts`, `src/lib/server/observability/sentry.ts`), so choosing Workers-friendly libraries only when/if a migration starts is low-risk; there's no reason to pay the Shiki-JS-engine or jsdom-alternative cost today.
- **CLI/device flow**: Already just `fetch` + DB writes; nothing about the current CLI OAuth device-flow design (`src/routes/api/v1/auth/device/`) would need to change for Workers.
